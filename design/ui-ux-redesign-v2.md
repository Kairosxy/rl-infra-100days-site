# RL Infra · UI/UX 重设计方案

> 适用范围：知识库首页、知识主题、工程案例、框架实现、快速复习与移动端。本文是界面与交互设计契约，**不是上线验收报告**。现有 Topic / Case / Implementation 数据模型保留，前端视觉及信息架构据此重构。

## 读者什么时候打开它

技术学习和工作查询是不同任务。首页需要让人用最少操作进入答案，而不是展示「这个系统有哪些功能」。

| 场景 | 用户当前想做什么 | 界面行为 |
|---|---|---|
| 会议前 30–90 秒 | 想起一个词但说不完整 | 搜索概念 → 直接读一段准确解释 → 可选「怎么向同事解释」 |
| 遇到训练异常 | 有现象，没有根因 | 搜索错误/指标 → 对应工程案例 → 可执行的排查顺序与反证 |
| 想真正理解机制 | 不满足于结论 | 进入 Topic 全文 → 公式/张量/反例 → 对应来源、代码或实验 |
| 比较工程方案 | 需要做实现选择 | 从 Case 或 Topic → 框架实现对照 → 支持版本、权衡、验证证据 |

成功不是点击量、答题字数、卡片数或每日完成率；成功是读者花更少时间找到准确的解释，并在需要时有足够材料验证技术判断。

## 产品级设计方向

选用 **Swiss Minimalism（瑞士式排版）+ Editorial Documentation（编辑式技术文档）**。不是模仿营销首页，而是借用工程文档的可浏览性、学术文章的长文可读性和工具应用的快捷操作。

- 采用紧凑、清楚的栅格；图、公式和代码以证据身份出现，不作为装饰。
- 内容优先。标题、正文、代码、图注决定层级，减少容器套容器和重复的英文标签。
- 配色限制在纸张米白、深灰墨色、深绿交互和少量用于异常/对照的土橘色。
- 不使用 Bento Grid、Glassmorphism、渐变 Dashboard、假 KPI、装饰英文眉题、大量图标或无意义卡片。
- 不在每篇文章结尾强制附「问答/实验/复习」，交互仅在确实能够检验某个反事实时出现。

### 设计 Token（初版）

| 语义 | 建议值 | 使用 |
|---|---|---|
| `--surface` | `#FAF9F6` | 页面背景 |
| `--paper` | `#FFFEFB` | 阅读与输入区域 |
| `--ink` | `#28342E` | 正文、标题 |
| `--secondary` | `#516157` | 次要内容，需通过对比度检查 |
| `--accent` | `#315B46` | 链接、Focus、选中 |
| `--warning` | `#AD7658` | 错误/未证实，不能仅以颜色传达 |
| `--line` | `#DFE4DC` | 必要分隔线 |
| `--space` | 4/8/12/16/24/32/48px | 主间距梯度 |

中文正文用系统中文无衬线字体为主（16px、行高 1.7–1.85），标题可适度使用宋体作为编辑式层次，但避免中文标题与 Georgia 英文产生突兀的字体回退。代码使用等宽字体，数字用 Tabular Numerals。桌面文章正文最大宽度建议 **720–760px**，避免长行阅读。

### 栅格

桌面宽屏：`224–240px` 左目录 + `720–760px` 正文 + `180–210px` 本文目录（只在有足够段落时出现）。顶部栏高度约 56–64px，不让它、侧栏和正文同时出现重叠的 Sticky 层。

中等宽度：关闭右侧 TOC，正文宽度优先。小屏（375px 起）：只显示正文，目录由显式按钮展开，正文锚点、返回行为和页面滚动保持完整；公式和表格自身可横向滚动，整页不可横向溢出。

## 页面应该怎样组织

### 首页：入口，而不是产品介绍

移除首页的「文章数量/题目数量/专题数量」统计栏、泛化的五阶段训练流程图，以及重复的“阅读路径”宣传文字。这些内容如有技术价值应进入对应 Topic。

建议布局：

~~~text
RL Infra                         知识  工程问题  框架实现  回顾
────────────────────────────────────────────────────────────
[搜索 PPO、FP8、R3、KV OOM、Partial Rollout…                  /]

基础知识
  RL 优化                 Learner 与数值
  并行训练                Serving 与 KV
  Agent 轨迹              异步训练
  OPD/蒸馏                性能诊断与研究

工程问题
  FP8 后 Logprob Gap 为什么变大？
  RL Step 变慢，真的是 Trainer 的问题？
  MoE Expert Routing 两侧为何不同？
  Group 数据足够了，GPU 为何仍在生成？

框架实现
  verl / HybridFlow   Megatron/FSDP2   SGLang/vLLM
  slime / AReaL       NeMo RL / R3     TransformerEngine
~~~

三种内容在主页面承担不同职责。不是平均分成三个大卡片，更不要在卡片内部重复一遍站点介绍。每行标题要像真正的技术文章标题，概述最多一行即可。

### 基础 Topic：像技术文章一样读

在文章第一屏呈现：面包屑、精准标题、一个关键结论或前提，以及自然衔接的正文。读者不需要先进入“学习模式”。

正文是连续的编辑式排版：推导、代码、表格和关键案例在需要的位置自然出现。左边是所属章节目录；右边仅在 H2/H3 足够多时显示章节锚点。关联 Case/Implementation 放在解释最适合的位置或文章末尾，并标明这两者与当前机制的关系。

「30 秒回想」不要在所有 Topic 第一屏强制占一张卡；可以是标题旁轻量动作，点击显示单句解释或有区分度的判断问题，**绝不默认出现作文输入框**。

### Case：以故障/决策现象开始

页面开头就是现象和诊断条件，例如：

> 开启 FP8 后，Response 变短，Rollout 和 Learner 的 Logprob Gap 扩大。第一步是比较同一份权重、同一 Token 与相同采样定义吗？

随后按真正的排查逻辑排列证据、反证与解法：区分采样分布问题、FP8 量化误差、MoE Router 分歧、Policy Version。若问题需要分支，就画判定树；若只需要一个对照表，就不创建互动实验。

解决方案旁标注：它修复哪种原因、改变了什么约束、付出什么代价、如何验证。框架实现从相应方案链接过去，不把 Case 文本复制一份。

### Implementation：框架为何做出这个取舍

在文章第一屏说明架构的一个核心决定，例如：为什么 AReaL 独立生成/训练服务，或者 NeMo RL 为什么要把 Router Metadata 传到 Learner。不要写公司宣传或空泛“生态优势”。

有证据时才给确切 Commit/Release、调用链、关键字段、配置和可运行最小例子；尚未核对源码时清晰区分“设计概要”与“已核实代码”。明确与其他框架相同/不同的机制及资源成本，不强制每篇都列一个统一的五维比较表。

### Review：恢复记忆，而不是交作业

默认每屏一道问题，可以直接点击「看解释」，不要求填写任何文字。解释先给核心逻辑，再有“详细推导”入口；需要记忆标记时仅一个“还不熟”，收藏/笔记放在次级操作里。没有进度 KPI、四个大数字卡片、答案模板和站点介绍文案。

会前速查是 Topic 的一种阅读方式，不需要另建一套重复维护的问答系统。原有 224 道题与本地数据键仍兼容。

## 交互与状态设计

- 顶层导航只负责三类知识与快速回顾；搜索是全站入口，`/` 可聚焦。不要同时使用功能等价的“知识库/检索/问题”作为互相竞争的主导航。
- 搜索结果按「知识解释」「工程案例」「框架实现」分组，标题与关键词高亮，键盘可选；查询时不应把已经展开的阅读页面频繁强制重置。
- 文章/案例/框架互相深链；浏览器前进/后退、搜索返回、文章小节锚点以及滚动焦点需保持正确。旧 `#day=N`、原题号和 `localStorage` 数据兼容。
- 只在机制随变量变化会产生高信息收益时允许组件嵌入，例如 PPO Clip 分段曲线、KV 内存预算、Async Timeline。用户不调参数也必须能通过文字与数值理解结论。
- 外部 MathJax/Mermaid 失败时，数学公式仍有可读文本、图示保留可见源码；延迟加载非关键库，避免首页加载论文图示引擎。

## 不要重复的 AI 化呈现

彻底删除以下惯例，而不是替换措辞：`WHAT YOU'LL LEARN`、`ANSWER FRAMEWORK`、`PERSONAL NOTES` 这种与内容无关的固定栏目；每章都用同样四步“背景-原理-案例-总结”；强制每日一图、一交互、一小测；把知识引用做成技术 Logo 墙；“恭喜你掌握了X”以及不提供证据的推荐语。

## 需要通过的验收

| 场景 | 验收条件 |
|---|---|
| 快速查问题 | 从首页搜索“FP8 Logprob Drift”到案例正文最多 2 次操作 |
| 会议前回忆 | 进入 PPO 概念后 30–60 秒内读到准确的可口述解释，无需输入 |
| 深入学习 | 同一 Topic 可以继续进入公式、代码与对应 Case/Implementation，不重复读通用说明 |
| 框架选型 | 比较页面能够指出方案实现位置、版本、代价和证据可靠性 |
| 移动端 | 375/768px 无整页水平滚动、遮挡/双导航、被 Sticky 区域遮住的聚焦内容 |
| 无障碍 | 正文字体正常对比度 ≥4.5:1；可键盘操作；Focus 可见；控件建议 44×44px；Reduced Motion 可用 |
| 正确性 | 原数据、URL、224 题、LocalStorage 不丢；搜索/返回/锚点状态一致；公式与图示退化可读 |
| 构建 | GitHub Actions + Playwright 在 375/768/1024/1440px 检查关键场景和截图 |

## 分阶段改造（避免继续缝补）

先建立设计 Token 和统一页面框架，移除重复导航与首页仪表盘结构；再实现四种内容状态（Home / Topic / Case / Implementation）与轻量 Review。随后校验正文排版、搜索/回退/移动 TOC，最后用真实的 PPO、FP8/R3、Async 三条完整路径做可用性验收。

**上线条件不是视觉截图“看着不错”**：必须同时通过阅读任务、交互状态与多尺寸浏览器测试。用户未明确授权前不覆盖此前用户自行修改的站点代码；设计稿先独立评审，落地按最新 HEAD 小步提交。
